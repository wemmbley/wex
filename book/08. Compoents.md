# Компоненты

Если вы пришли из мира jQuery, скорее всего ваш код выглядит примерно так:
большой HTML-файл, много $('.что-то').on(...), и всё в одном месте.
Это работает — но когда проект растёт, один и тот же кусок разметки
начинает копироваться по странице, а правка в одном месте требует правки
во всех остальных.

Компонент — это переиспользуемый кусок шаблона со своим стейтом.
Один раз описали карточку товара, кнопку или иконку — и вставляете их в
любое место как обычный HTML-тег. WEX сам разберётся как это отрисовать.

Дальше мы пройдём весь путь по порядку: сначала компоненты внутри единой страницы,
потом вынесем их в отдельные файлы, научим общаться между собой,
дадим им общий стейт и в конце разберёмся, как не грузить лишнее.

# Компоненты внутри единой страницы

## Первый компонент — иконка

Представьте что по всему сайту используются иконки, и каждый раз писать
`<i class="icon icon-search"></i>` надоело. Вынесем это в компонент:

```js
const { component } = window.jqvm

const icon = $(`<i class="icon icon-{{type}}"></i>`)
  .state(() => ({ type: 'eye' })) // начальное значение по умолчанию

component('icon', icon)
```

Теперь в любом шаблоне можно писать просто:
```html
<template id="app">
    <icon type="search"></icon>
    <icon type="heart"></icon>
    <icon type="user"></icon>
</template>
```

WEX подставит нужный тип и каждый раз отрисует правильную иконку.
Захотели изменить структуру иконки — меняете в одном месте, обновится везде.

```
Заметьте: в .state() передаётся функция, которая возвращает объект —
а не сам объект напрямую. Это важно: каждый экземпляр компонента
получает свою независимую копию стейта. Если передать объект напрямую —
все иконки на странице будут делить один стейт и менять друг друга.
```

## Пропсы — передача данных внутрь

Пропсы это то что вы передаёте компоненту снаружи — как атрибуты HTML-тега.
Есть три способа:

Обычная строка — просто пишете значение:
```html
<icon type="search"></icon>
```
Выражение из стейта — ставите : перед именем,
и WEX вычислит значение из текущего стейта родителя:
```html
<icon :type="currentIcon"></icon>
<!-- currentIcon берётся из state родительского шаблона -->
```
Функция-обработчик — ставите @, чтобы компонент мог сообщить родителю о событии:
```html
<my-button @click="handleClick"></my-button>
```

Важное ограничение: работают только те пропсы, которые объявлены в стейте компонента.
Если в стейте компонента нет ключа color — передать color="red" снаружи не получится,
атрибут просто проигнорируется.

```js
// стейт компонента
.state(() => ({ type: 'eye', size: 'md' }))

// ✓ сработает — оба ключа есть в стейте
<icon type="search" size="lg"></icon>

// ✗ не сработает — color нет в стейте компонента
<icon type="search" color="red"></icon>
```

Регистр в именах пропсов не важен: HTML приводит атрибуты к нижнему регистру,
поэтому `:mobileMenu="mobileMenu"` WEX сопоставит с ключом `mobileMenu` в стейте компонента сам.

## Компонент карточки — реальный пример

Сделаем компонент карточки товара, который можно переиспользовать в каталоге:
```js
const productCard = $(`
    <template>
        <div class="card">
            <img w-src="image" alt="Фото">
            <h3>{{ name }}</h3>
            <p>{{ price }} ₽</p>
            <button class="buy-btn">Купить</button>
        </div>
    </template>
`)
  .state(() => ({
      name: '',
      price: 0,
      image: '',
  }))
  .method('buy', state => function(e) {
      alert(`Добавлено в корзину: ${state.name}`)
  })
  .on('click', '.buy-btn', function(state) {
      this.fn('buy')(state)
  })

component('product-card', productCard)
```

Используем в шаблоне через w-for:
```html
<template id="catalog">
    <div class="catalog">
        <product-card
            w-for="item in products traceby item.id"
            :name="item.name"
            :price="item.price"
            :image="item.image">
        </product-card>
    </div>
</template>

<script>
    $('#catalog')
      .state({
          products: [
              { id: 1, name: 'Хлеб',   price: 45,  image: '/img/bread.jpg'  },
              { id: 2, name: 'Молоко', price: 89,  image: '/img/milk.jpg'   },
              { id: 3, name: 'Сыр',    price: 320, image: '/img/cheese.jpg' },
          ]
      })
      .mount()
</script>
```
Три карточки — три независимых компонента, каждый со своим стейтом.

## Эмиттер — компонент говорит с родителем

Пока что данные шли только в одну сторону: родитель передаёт пропсы — компонент
их отображает. Но что если компонент хочет сообщить родителю что что-то произошло?
Для этого есть `emit`.

Представьте компонент-счётчик, который должен уведомлять родителя об изменении значения:
```js
const counter = $(`
    <template>
        <button class="minus-btn">−</button>
        <span>{{ count }}</span>
        <button class="plus-btn">+</button>
    </template>
`)
  .state(() => ({ count: 0 }))
  .on('click', '.plus-btn', state => function() {
      state.count++
      this.emit('change', state.count) // ← сообщаем родителю
  })
  .on('click', '.minus-btn', state => function() {
      state.count--
      this.emit('change', state.count) // ← сообщаем родителю
  })

component('counter', counter)
```
Родитель подписывается через `@change` и регистрирует обработчик через `.fn()`:
```html
<template id="app">
    <counter @change="onCountChange"></counter>
    <p>Родитель знает: {{ total }}</p>
</template>

<script>
    $('#app')
      .state({ total: 0 })
      .method('onCountChange', state => function(newCount) {
          state.total = newCount
      })
      .mount()
</script>
```
Компонент живёт своей жизнью внутри, но в нужный момент «кричит наружу»
через `emit` — родитель слышит и реагирует.

## Локальный компонент vs глобальный

Если компонент нужен только в одном конкретном шаблоне — регистрируйте его
локально через `.component()` прямо на вью. Если нужен по всему приложению —
регистрируйте глобально через `component()` из импорта:

```js
// Глобально — доступен везде
const { component } = window.jqvm
component('my-icon', icon)

// Локально — только для этого шаблона
$('#app')
  .state({ ... })
  .component('my-icon', icon) // ← метод самого вью
  .mount()
```

Локальный компонент виден только в том шаблоне, на котором вы его зарегистрировали.
Дочерние компоненты его не наследуют: если иконка нужна внутри карточки,
регистрируйте её глобально или повторите `.component()` на самой карточке.

# Компоненты в отдельных файлах

## Загружаемые компоненты по URL'у

Когда компонентов становится много, держать их в одном JS-файле неудобно.
Каждому можно отвести свой HTML-файл — и подключать по ссылке.

Пример готового компонента `Button.html`:
```html
<template>
    <slot></slot>
    <br>
    <button class="btn">
        {{ label }}: {{ count }}
    </button>
</template>

<script type="module">
    export default ($component) => $component
        .state({
            label: 'Кликов',
            count: 0
        })
        .method('buy', state => () => {
            state.count++
        })
        .on('click', '.btn', function (state) {
            return this.method('buy')(state)
        })
</script>
```
Как видите, ничего сложного. Разница от обычного кода в
`<script type="module">` и вместо обычной инициализации
мы пишем `export default ($component) => $component`.

Если компоненту не нужна логика, `<script>` можно вообще не писать:
достаточно одного `<template>`, и WEX сделает из него компонент без стейта.

Вызов компонента внутри ДРУГОГО файла `Index.html`:
```html
<template id="component-test">
    <my-button>Welcome!</my-button>
</template>

<script>
    $('#component-test')
        .state()
        .component('my-button', 'button.html')
        .mount()
</script>
```
Как видим, ничего сложного. Указываем имя компонента и его ссылку
прямую или относительную - `.component('my-button', 'button.html')`.

Всё что вы напишете между тегами (`Welcome!` в примере выше) попадёт в то место,
где в шаблоне компонента стоит `<slot></slot>`. Так можно передавать в компонент
не только значения, но и целые куски разметки.

Пока файл скачивается, на месте компонента пусто. Как только он готов,
WEX перерисует родителя сам, ничего делать не нужно.

## Ленивые компоненты по URL'у

Обычный компонент по ссылке начинает скачиваться сразу, как только вы его зарегистрировали:

```js
.component('Article', 'Components/Article.html')
```

Если страница «Статья» открывается не у каждого посетителя, это лишний трафик.
Третьим аргументом можно сказать «не торопись»:

```js
.component('Article', 'Components/Article.html', { lazy: true })
```

Теперь файл скачается в одном из двух случаев:

- тег `<Article>` впервые попал в шаблон, который рендерится прямо сейчас
- его заранее прогрела ссылка `<Link>` (см. документацию роутера)

Заметьте: тег внутри скрытого блока `w-route` или `w-if` в шаблон не попадает.
Пока блок скрыт, компонент не грузится — и это именно то, что нужно.

## Что если загрузка не удалась

Сеть на мобильном бывает капризной, поэтому WEX не сдаётся с первой попытки:
он пробует скачать компонент до трёх раз, делая всё более длинные паузы.
Если и это не помогло, в консоли появится ошибка с адресом файла,
а следующий рендер или наведение на ссылку попробует снова. Компонент не «ломается навсегда».

Ещё две ошибки, которые вы можете встретить в консоли:

- `no <template>` — в файле нет тега `<template>`
- `must export default a function returning a view` — в `<script type="module">`
  забыли `export default` или функция не вернула `$component`

# Общий стейт между компонентами

## Синхронизация компонентов между собой общим стейтом

Когда компонентов на странице становится больше одного, возникает естественный
вопрос: а что если им нужно работать с одними и теми же данными?

Представьте корзину на сайте. Счётчик товаров в шапке, список товаров в боковой
панели и итоговая сумма в футере — три разных компонента, но все они должны
знать об одном и том же: что сейчас лежит в корзине. Если каждый хранит свою
копию стейта — они начнут расходиться и показывать разное.

Store — это единый стейт который несколько компонентов разделяют между собой.
Меняется значение в одном месте — все компоненты которые его используют
обновляются одновременно автоматически.

## Как это работает

```js
// Создаём общий стейт — один на всех
const store = shareState({ count: 10 })

// Оба компонента получают один и тот же store вместо своего стейта
const componentA = $('<span>Значение: {{count}}</span>')
  .state(store)

const componentB = $('<div>count: {{count}}</div>')
  .state(store)
```

```html
<template id="app">
    <comp-a></comp-a>
    <comp-b></comp-b>
</template>
```

```js
$('#app').state({})
  .component('comp-a', componentA)
  .component('comp-b', componentB)
  .mount()
```

Оба компонента видят одно и то же count. Если count изменится — оба перерисуются.

## Реальный пример — счётчик корзины

Сделаем кнопку добавления товара и счётчик в шапке — два независимых
компонента которые работают с одними данными:

```js
// Единый источник правды для всей страницы
const cartStore = shareState({
    itemCount: 0,
    total: 0,
})

// Шапка — только показывает
const cartBadge = $(`
    <template>
        <div class="cart-badge">
            🛒 <span>{{ itemCount }}</span>
        </div>
    </template>
`)
  .state(cartStore)

// Кнопка — только добавляет
const addToCart = $(`
    <template>
        <button class="add-btn">Добавить в корзину ({{ itemCount }})</button>
    </template>
`)
  .state(cartStore)
  .on('click', '.add-btn', state => {
      state.itemCount++
  })
```

```html
<template id="app">
    <cart-badge></cart-badge>

    <main>
        <h2>Товар: Хлеб — 45 ₽</h2>
        <add-to-cart></add-to-cart>
    </main>
</template>

<script>
    $('#app').state({})
      .component('cart-badge', cartBadge)
      .component('add-to-cart', addToCart)
      .mount()
</script>
```

Нажали кнопку — itemCount вырос на единицу в cartStore — оба компонента мгновенно
перерисовались с новым значением. Никакой передачи данных через пропсы, никаких
событий наверх — просто общий стейт.

## Store + localStorage

Store прекрасно сочетается с механизмом storage который мы разбирали раньше.
Достаточно добавить ключ storage в shareState — и общий стейт автоматически
переживёт перезагрузку страницы:

```js
const cartStore = shareState({
    storage: {
        itemCount: 0,
        total: 0,
    }
})
```

Теперь пользователь добавил товары, закрыл вкладку, вернулся — корзина на месте.
И по-прежнему все компоненты синхронизированы между собой.

## Когда использовать Store, а когда пропсы

Не каждый стейт нужно выносить в Store. Хорошее правило:

Пропсы — когда данные принадлежат родителю и он осознанно передаёт их вниз.
Например, родитель знает имя пользователя и передаёт его в дочерний компонент-приветствие.

Store — когда данные нужны нескольким компонентам которые не знают друг о друге и не имеют
общего родителя. Корзина, авторизация, выбранная тема — всё что является глобальным
состоянием приложения.

```
Локальный стейт    →  данные нужны только этому компоненту
Пропсы             →  родитель осознанно делится данными с ребёнком
Store              →  данные нужны нескольким несвязанным компонентам
```

```
Store это не серебряная пуля — не стоит тащить туда всё подряд.
Если данные нужны только одному компоненту, пусть живут в его локальном стейте.

Store появляется тогда, когда без него начинается неудобная передача данных
через длинные цепочки пропсов или костыльные глобальные переменные.
```

# Асинхронные компоненты

Когда приложение растёт, на одной странице может собраться десяток компонентов.
Если грузить их все сразу — пользователь ждёт пока загрузится всё, даже то что ему
сейчас не нужно. Модальное окно которое откроется только если нажать кнопку, редактор
который появится только в режиме редактирования — зачем тащить их при первой загрузке?

Асинхронный компонент — это компонент который загружается только тогда когда действительно
понадобился. Страница открывается быстро с минимумом кода, а тяжёлые части подгружаются
по требованию в фоне.

Ленивые компоненты по URL'у (`{ lazy: true }`), о которых мы говорили выше, решают ту же задачу
для HTML-файлов. `createAsyncComponent` — более общий инструмент: загрузчик вы пишете сами,
и он может вернуть что угодно, будь то JS-модуль или HTML с вашего бэкенда.

## Простейший случай — ленивая загрузка модуля

Компонент живёт в отдельном JS-файле и загружается только когда страница его запрашивает:
```js
// components/user-card.js — отдельный файл
export default $(`
    <template>
        <div class="user-card">
            <h3>{{ name }}</h3>
            <p>{{ email }}</p>
        </div>
    </template>
`)
  .state(() => ({ name: '', email: '' }))
```
```js
// main.js — основной файл
const { createAsyncComponent } = window.jqvm

$('#app')
  .state({ user: { name: 'Алиса', email: 'alice@astre.ws' } })
  .component(
      'user-card',
      createAsyncComponent(() => import('./components/user-card.js'))
  )
  .mount()
```
```html
<template id="app">
    <user-card :name="user.name" :email="user.email"></user-card>
</template>
```
Браузер загрузит `user-card.js` отдельным запросом — и только тогда когда шаблон
встретит тег `<user-card>`. До этого момента файл не скачивается вовсе.

## Загрузка с индикатором — реальный сценарий

Асинхронная загрузка занимает время, и пользователь должен понимать что что-то происходит.
Для этого у `createAsyncComponent` есть второй аргумент — `callback` который вызывается когда
компонент загрузился:
```html
<template id="app">
    <div w-if="!!loading" class="spinner">
        Загружаем редактор...
    </div>
    <rich-editor w-if="!loading"></rich-editor>
</template>

<script>
    const { createAsyncComponent } = window.jqvm

    $('#app')
        .state({ loading: true })
        .component(
            'rich-editor',
            createAsyncComponent(
                // loader — как загрузить компонент
                () => import('./components/rich-editor.js'),

                // callback — что сделать когда загрузился
                function() {
                    this.update({ loading: false })
                }
            )
        )
        .mount()
</script>
```
Пользователь видит спиннер пока компонент грузится. Как только загрузка завершилась
— loading становится false, спиннер исчезает, редактор появляется.

## Загрузка HTML с сервера

Компонент не обязательно должен быть JS-модулем. Можно загрузить HTML прямо с сервера
через Ajax — удобно когда шаблоны живут на бэкенде:

```js
$('#app')
  .state({ loading: true })
  .component(
      'product-table',
      createAsyncComponent(
          // загружаем HTML через jQuery Ajax
          () => $.get('/components/product-table.html')
            .then((html) => {
                return $(html).vm(() => ({
                    products: [],
                    sortBy: 'name',
                }))
            }),

          function() {
              this.update({ loading: false })
          }
      )
  )
  .mount()
```

Сервер отдаёт кусок HTML, WEX оборачивает его в вью с нужным стейтом — и компонент готов.
Это особенно хорошо сочетается с PHP и Blade: шаблоны хранятся на сервере,
подгружаются по необходимости, данные приходят реактивно.

## Реальный кейс — тяжёлый редактор по клику

Самый частый сценарий применения — откладывать загрузку тяжёлых компонентов до момента
когда пользователь явно их запросил:
```html
<template id="app">
    <div w-if="!editorOpen">
        <p>{{ previewText }}</p>
        <button class="edit-btn">Редактировать</button>
    </div>

    <div w-if="!!editorOpen">
        <div w-if="!!editorLoading">Загружаем редактор...</div>
        <obsidian-editor w-if="!editorLoading"></obsidian-editor>
        <button class="cancel-btn">Отмена</button>
    </div>
</template>

<script>
    const { createAsyncComponent } = window.jqvm

    $('#app')
        .state({
            previewText: 'Нажмите редактировать чтобы изменить текст.',
            editorOpen: false,
            editorLoading: false,
        })
        .component(
            'obsidian-editor',
            createAsyncComponent(
                () => import('./components/obsidian-editor.js'),
                function() {
                    this.update({ editorLoading: false })
                }
            )
        )
        .on('click', '.edit-btn', state => {
            state.editorOpen   = true
            state.editorLoading = true
        })
        .on('click', '.cancel-btn', state => {
            state.editorOpen   = false
            state.editorLoading = false
        })
        .mount()
</script>
```

Пользователь открывает страницу — редактор даже не начинает загружаться.
Нажал «Редактировать» — только тогда браузер идёт за файлом.
Тяжёлые библиотеки не тормозят первую загрузку страницы.

## Какой способ ленивой загрузки выбрать

У WEX теперь два способа не грузить лишнее. Выбор простой:

```
HTML-файл с <template> и <script type="module">  →  .component(name, url, { lazy: true })
JS-модуль, HTML с бэкенда, свой загрузчик         →  createAsyncComponent(...)
Данные внутри списка, комментарии, переписка      →  w-lazy (см. документацию по ленивой загрузке)
```

## Когда использовать асинхронные компоненты

Не каждый компонент нужно делать асинхронным — это усложняет код и добавляет лишний
сетевой запрос. Хорошие кандидаты:

Грузите асинхронно если компонент тяжёлый (редакторы, графики, карты), показывается
не сразу (модалки, табы, аккордеоны) или нужен только части пользователей
(формы редактирования, админские панели).

Грузите сразу если компонент маленький, нужен при первой загрузке или
является частью основного интерфейса который пользователь видит всегда.

```
Маленькая кнопка, иконка           → обычный компонент
Шапка сайта, главное меню          → обычный компонент
Модальное окно                     → async
Текстовый редактор                 → async
Интерактивная карта                → async
Графики и дашборды                 → async
Форма которая открывается по клику → async
```

```
Асинхронные компоненты — это не оптимизация ради оптимизации.
Это инструмент для конкретной задачи: сделать первую загрузку страницы быстрой,
а тяжёлые части подтягивать только тогда когда они действительно нужны.
```

# Под капотом: что WEX делает за вас

## Рекурсивные компоненты

Компонент может вставлять сам себя: комментарии с ответами, дерево меню, вложенные папки.
Чтобы случайная ошибка не повесила вкладку, WEX ограничивает глубину вложенности —
по умолчанию 50 уровней. Дальше компонент не создаётся, в консоль падает ошибка
с цепочкой компонентов, а на месте проблемного элемента появляется атрибут `data-wex-error="max-depth"`.

Если вы видите такую ошибку, значит у рекурсии нет условия выхода.
Остановите её через `w-if`:

```html
<template>
    <div class="comment">
        {{ comment.text }}
        <comment w-for="reply in comment.replies || []" :comment="reply"></comment>
    </div>
</template>
```

## Много компонентов сразу

Когда на странице сотни компонентов (например, полторы тысячи комментариев),
монтировать их все в одном кадре — значит повесить интерфейс. Поэтому WEX создаёт
первые 50 компонентов сразу, а остальные ставит в очередь и монтирует по кадрам,
укладываясь примерно в 10 мс на кадр. Страница остаётся живой, а порядок остаётся
таким же, как в документе.

## Подсказки в консоли

На localhost WEX подсказывает, что пошло не так: проп получил `undefined`,
выражение в `{{ }}` вернуло пустоту, в `w-src` пришло ничего. В каждой подсказке есть
цепочка компонентов (`app › posts › card`), выражение и доступные переменные —
сразу видно, где именно сломалось. На продакшене остаются только настоящие ошибки.

## Вся идея в одной строке

Компоненты в WEX — это те же самые вью, просто вложенные друг в друга.
Всё что умеет обычный шаблон: стейт, директивы, хуки, `w-for`, `w-if` —
всё это работает и внутри компонента. Никакого нового синтаксиса учить не нужно.
